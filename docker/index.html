Cómo correr el laboratorio en tu computador

Tres comandos. Necesitas Docker instalado localmente (no en la nube).

docker pull fabiguaza76/inforense:v1
docker run -d --name lab-forense -p 8080:80 fabiguaza76/inforense:v1
# Abrí http://localhost:8080/ en tu navegador

Si tienes Apple Silicon (M1/M2/M3/M4), el laboratorio es x86 y funcionará con la emulación de Docker Desktop, aunque más lento. Para mejor experiencia, usa un equipo Intel o AMD con 8 GB RAM y 25 GB libres.

Caso 1 · Fundamentos

Hashes, integridad y rótulos · Lo que enseña un perito cuando apenas empieza.

En una frase. Calcule y verifique el SHA-256 del acta del caso, distinga entre integridad y autenticidad, y llene un rótulo de cadena de custodia.

Qué va a hacer

Tres pasos. Abra una terminal dentro del contenedor (en la web del laboratorio, hay una terminal interactiva) y ejecute los comandos.

Paso 1 · Calcule el SHA-256 del acta

sha256sum /evidencia/caso1/acta.txt

Va a obtener 64 caracteres hexadecimales. Anótelos.

Paso 2 · Verifique con el archivo .sha256

sha256sum -c /evidencia/caso1/acta.sha256

Si la huella coincide, el sistema responde acta.txt: OK.

Paso 3 · Identifique el archivo

file /evidencia/caso1/acta.txt

Lo que entrega

Un mini-informe (cinco líneas, en ~/trabajo/caso1.txt) con:

  1. El SHA-256 calculado en el Paso 1.
  2. Si coincide con el del Paso 2 (Sí/No).
  3. El tipo de archivo que reporta file.
  4. La fecha del cálculo.
  5. Conclusión: "La integridad del acta está demostrada" o detalle de qué falló.

Errores que se cometen

"Pego el hash y ya está"
Sin sha256sum -c, solo pegó números. El -c es el procedimiento legal.
"MD5 es lo mismo"
MD5 tiene colisiones prácticas desde 2004. Use SHA-256 como hash principal.
"El hash prueba que no se modificó"
Prueba integridad bit-a-bit respecto al momento del cálculo. NO prueba autoría ni veracidad.
"Modifiqué el acta para corregir una fecha"
Modificar = nuevo hash = cadena rota. Use un documento de "fe de erratas" con su propio hash.

Caso 2 · Adquisición y cadena de custodia

Copia forense verificada con hash · Lo que distingue a un perito serio.

En una frase. Genere una copia forense verificada por hash de la imagen FAT32 y verifique el directorio de evidencia con hashdeep.

Qué va a hacer

Cinco pasos. La imagen FAT32 está en /evidencia/caso2/caso2-fat32.img.

Paso 1 · Identifique la imagen

file /evidencia/caso2/caso2-fat32.img

Paso 2 · Calcule SHA-256 de la imagen

sha256sum /evidencia/caso2/caso2-fat32.img

Paso 3 · Hash recursivo del directorio

hashdeep -r /evidencia/caso2/evidencia_original/ > ~/trabajo/caso2-hashes.txt
hashdeep -r -k ~/trabajo/caso2-hashes.txt /evidencia/caso2/evidencia_original/

Paso 4 · Copia forense con dc3dd

dc3dd if=/evidencia/caso2/caso2-fat32.img \
      of=~/trabajo/caso2-copia.dd \
      hash=sha256 hashlog=~/trabajo/caso2-copia.hashes \
      log=~/trabajo/caso2-copia.log bs=4M

Paso 5 · Verifique la copia

diff <(sha256sum ~/trabajo/caso2-copia.dd | awk '{print $1}') \
     <(grep -oE "[0-9a-f]{64}" ~/trabajo/caso2-copia.hashes)

Errores que se cometen

"Solo copié con cp"
cp modifica timestamps. Use dc3dd que calcula hash durante la copia.
"Calculé el hash antes y después, son iguales"
Eso prueba que no cambió DESPUÉS, no que la copia sea idéntica al ORIGINAL.
"dd me sirve igual"
Funciona pero NO calcula hash ni deja bitácora. dc3dd sí.

Caso 3 · Análisis de sistemas de archivos y SO

MFT, flujos alternos y recuperación · El pan de cada día del perito de Windows.

En una frase. Examine el volumen NTFS con Sleuth Kit y detecte archivos borrados y flujos alternos (ADS).

Qué va a hacer

Cuatro pasos. Imagen NTFS: /evidencia/caso3/caso3-ntfs.img.

Paso 1 · Identifique el filesystem

file /evidencia/caso3/caso3-ntfs.img

Paso 2 · Liste el directorio raíz

fls /evidencia/caso3/caso3-ntfs.img

Paso 3 · Inspeccione metadatos de un inodo

istat /evidencia/caso3/caso3-ntfs.img <INODO>

Paso 4 · Archivos borrados

fls -d /evidencia/caso3/caso3-ntfs.img

Errores que se cometen

"Copié y monté la imagen"
Montar modifica timestamps. Use Sleuth Kit sin montar.
"fls no muestra ADS"
Use istat por inode; los ADS viven en atributos $DATA adicionales.
"El archivo borrado es irrecuperable"
Mientras el espacio no se sobrescriba, está. Use icat imagen <INODO> > recuperado.bin.
"Confundí MFT con MBR"
MFT = base de datos interna de NTFS. MBR = primer sector con tabla de particiones.

Caso 4 · Forense de redes y memoria

Tráfico PCAP y captura de memoria del propio proceso · Análisis selectivo.

En una frase. Detecte dominios DGA-style y canales de C&C en un PCAP con tshark, y capture y analice la memoria de un proceso con gcore + Volatility 3.

Parte A · Red (PCAP)

tshark -r /evidencia/caso4/red_caso4.pcap -c 5
tshark -r /evidencia/caso4/red_caso4.pcap -Y "dns" | wc -l
tshark -r /evidencia/caso4/red_caso4.pcap \
       -Y "dns.qry.name matches '[0-9a-f]{16,}\.test'" \
       -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head -10
tshark -r /evidencia/caso4/red_caso4.pcap -Y "tcp.dstport == 8443" \
       -T fields -e frame.time_epoch

Parte B · Memoria del proceso

En dos terminales dentro del contenedor. Una con:

incidente

La otra con:

capturar-memoria
vol -f ~/trabajo/memoria_incidente_*.core linux.pslist
vol -f ~/trabajo/memoria_incidente_*.core linux.netscan
strings ~/trabajo/memoria_incidente_*.core | grep -i "c2.example.test"

Errores que se cometen

"La captura tiene MUCHOS paquetes, no los analizo todos"
El análisis es selectivo: use filtros.
"Encontré un dominio DGA, eso es malware"
Es un INDICIO, no prueba. La prueba se construye con conjunción de indicadores.
"memoria.lime es lo mismo que memoria.core"
No. .lime es formato LiME; .core es ELF Core de gcore.

Caso 5 · Dictamen pericial integrador

Las nueve partes del dictamen y las diez declaraciones · Lo que se evalúa en la sustentación oral.

En una frase. Redacte el dictamen pericial formal citando la evidencia recolectada en los casos 1-4.

Estructura (9 partes, art. 226 CGP)

  1. Encabezado e identificación del perito.
  2. Solicitud.
  3. Objeto del dictamen. Tres preguntas concretas.
  4. Marco normativo. Ley 906 arts. 415/417/420, CGP art. 226, Ley 1273 art. 269A, ISO/IEC 27037, ACPO, RFC 3227.
  5. Metodología y verificación de integridad.
  6. Hallazgos. Cuatro o cinco con evidencia, procedimiento y resultado numérico.
  7. Interpretación. Por qué importa cada hallazgo. Sin adjetivos.
  8. Conclusiones. Lista corta (3-6) que responden al Objeto.
  9. Firma y cierre + 10 declaraciones bajo juramento.

Diez declaraciones bajo juramento

Declaro bajo juramento que: (1) he examinado personalmente la evidencia; (2) el dictamen refleja fielmente mi análisis; (3) no tengo interés directo en el resultado; (4) no he recibido instrucciones sobre las conclusiones; (5) los métodos utilizados son reconocidos por la comunidad científica; (6) los hechos descritos son exactos; (7) no he omitido nada; (8) las opiniones están fundadas; (9) la cadena de custodia está documentada; (10) cumplo los requisitos del artículo 226 del CGP.

Errores que se cometen

"Pongo adjetivos que no probé"
Evite obviamente, claramente, evidentemente, sin duda, malicioso, sospechoso, con la intención de, hacker.
"No cito hashes específicos"
Cada hallazgo necesita SHA-256, conteo o fecha. Sin números son afirmaciones.
"Olvido una declaración jurada"
Las DIEZ. Si falta una, no es admisible.
