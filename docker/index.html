Laboratorio de Informática Forense

Universidad de Cataluña · Ingeniería Informática · Cohorte 2026-II

Cómo correr el laboratorio en tu computador

Antes de los casos: instalar Docker, descargar la imagen, arrancar el contenedor, abrir el navegador.

¿Qué es Docker?

Docker es un programa que ejecuta "mini-computadoras" virtuales dentro de tu computador. Cada una se llama contenedor y arranca en segundos con todo preinstalado: las 56 herramientas forenses (Sleuth Kit, tshark, Volatility 3, etc.), la evidencia sintética (imágenes FAT32, NTFS, PCAP) y los enunciados.

El laboratorio corre 100% en tu computador. No toca internet después de descargar la imagen.

Paso 1 · Instala Docker

SistemaInstrucciones
Windows 10/11docs.docker.com/desktop/install/windows-install/
Abre el instalador, sigue los pasos, reinicia si lo pide.
macOSdocs.docker.com/desktop/install/mac-install/
Descarga .dmg, arrastra Docker a Aplicaciones, ábrelo.
Ubuntu/Debiansudo apt-get update + sudo apt-get install docker.io

Verifica con docker --version (debe mostrar algo como Docker version 24.0.7).

Paso 2 · Descarga la imagen

docker pull fabiguaza76/inforense:v1

Tarda 2-10 minutos. Solo lo haces una vez; después queda en tu disco.

Paso 3 · Arranca el contenedor por PRIMERA VEZ

docker run -d --name lab-forense -p 8080:80 --memory=2g fabiguaza76/inforense:v1

Las cuatro partes hacen:

  • -d el contenedor corre en segundo plano, tu terminal queda libre.
  • --name lab-forense le da un nombre para manejarlo después.
  • -p 8080:80 mapea el puerto 80 del contenedor al 8080 de tu computador.
  • --memory=2g limita la RAM a 2 GB (suficiente).

Imprime un ID largo (por ejemplo abc123def456...).

Paso 4 · Abre el laboratorio en tu navegador

http://localhost:8080/

Vas a ver el portal con cinco pestañas de casos. Esta es tu puerta de entrada.

Paso 5 · Si ya tienes un contenedor llamado lab-forense (error frecuente)

Esto pasa cuando:

  • Detuviste el contenedor (docker stop lab-forense) y ahora quieres volver a arrancarlo.
  • Ya lo creaste una vez y estás intentando crearlo otra vez.

Síntoma: mensaje "container name already in use".

Diagnóstico: Ver todos los contenedores, no solo los corriendo.

docker ps -a

El contenedor lab-forense debe aparecer con STATUS Exited (si lo detuviste) o Up (si está corriendo).

Caso A — Querés volver a arrancarlo conservando los datos y los puertos:

docker start lab-forense
# NO uses -p aquí: docker start NO acepta -p.
# Los puertos ya están registrados desde el docker run original.
# Si la imagen fue creada con -p 8080:80, el puerto se vuelve a publicar solo.

Verificá que volvió a levantar:

docker ps
# Debe decir "Up X seconds" para lab-forense.
# Si no carga http://localhost:8080/, es porque tu docker run
# original NO tenía -p 8080:80, y hay que recrearlo (ver Caso B).

Caso B — Querés borrarlo y empezar fresco con puertos correctos:

docker rm -f lab-forense
docker run -d --name lab-forense -p 8080:80 --memory=2g fabiguaza76/inforense:v1

docker rm -f borra el contenedor (no la imagen). Después docker run lo recrea desde cero con el puerto bien publicado.

Por qué docker start -p no funciona: docker start solo reanuda contenedores detenidos; no acepta modificar la configuración de puertos. La opción -p (publish) es exclusiva de docker run. Si querés cambiar el puerto después de creado, hay que borrarlo y recrearlo.

docker stop lab-forense

El contenedor se apaga pero la imagen (1.2 GB) queda en disco.

Caso 1 · Fundamentos: hashes e integridad

Práctica guiada: lo que enseña un perito cuando apenas empieza — el acta debe ser idéntica bit a bit a la que se firmó en el momento de la cadena de custodia.

Objetivo

Calcular y verificar el hash SHA-256 del acta del caso, demostrar que la copia es idéntica al original, y dejar un mini-informe con los resultados.

Herramientas que vas a usar

ComandoQué hacePertenece a
sha256sumCalcula un hash SHA-256 de un archivo. Devuelve 64 caracteres hexadecimales (256 bits).GNU coreutils (viene con Linux)
sha256sum -cVerifica un archivo contra su hash guardado en otro archivo. Dice "OK" o "FAILED".GNU coreutils
fileIdentifica el tipo de archivo (texto, binario, UTF-8, etc.).GNU file

Qué hace un forense real

En un caso real, el perito recibe un dispositivo (celular, USB, disco). Lo conecta con un bloqueador de escritura, calcula el hash con sha256sum, hace la copia bit a bit con dc3dd (que vuelve a calcular el hash durante la copia), y al final verifica que ambos hashes coincidan. Si coinciden, la copia es exacta. Si difieren por UN solo bit, la copia se repite desde cero. Aquí simulamos el mismo flujo pero con un archivo de texto en lugar de un disco, porque la operación es la misma: producir un hash y verificarlo.

Paso 1 · Calcular el SHA-256

Qué hace un forense real

Lo primero al recibir una evidencia es calcular su huella digital. Esa huella se anota en el acta y nunca debe cambiar, porque es la prueba de que el archivo es el que se firmó en el momento de la cadena de custodia.

Herramienta

sha256sum <archivo> — calcula SHA-256 de cualquier archivo. Salida: <hash> <nombre_archivo>.

Escribe esto en la terminal

sha256sum /evidencia/caso1/acta.txt

Lo que vas a ver en tu pantalla

9f16b46c23373fdc1edcd5bb93c2841682e82bf0db95585d4b3cb44ead67abbc  /evidencia/caso1/acta.txt

La primera columna es el hash (64 caracteres hex: 0-9 y a-f). La segunda es el nombre del archivo.

Cómo verificas que funcionó

Anota el hash completo. Esa misma huella debe coincidir con la que está guardada en /evidencia/caso1/acta.sha256. Lo confirmamos en el siguiente paso.

Truco: si quieres solo el hash sin el nombre del archivo, usa sha256sum <archivo> | awk '{print $1}'.

Paso 2 · Verificar con el archivo .sha256

Qué hace un forense real

El archivo .sha256 contiene la huella que se calculó en el momento del empaque de la evidencia. Al volver a calcularla con sha256sum, debe coincidir. Si difiere, alguien modificó el archivo (o el disco se corrompió). En ambos casos hay que investigar.

Herramienta

sha256sum -c <archivo.sha256> — verifica que el archivo listado en .sha256 coincida con la huella guardada. Salida: <archivo>: OK o FAILED.

Escribe esto

sha256sum -c /evidencia/caso1/acta.sha256

Lo que vas a ver

/evidencia/caso1/acta.txt: OK

Si ves FAILED en lugar de OK

Significa que el archivo fue modificado. NO deberías ver eso porque el archivo viene de solo lectura en el contenedor; pero si pasara, sería un caso grave.

Paso 3 · Identificar el tipo de archivo

Herramienta

file <archivo> — inspección rápida: dice si es texto, binario, comprimido, etc.

Escribe esto

file /evidencia/caso1/acta.txt

Lo que vas a ver

/evidencia/caso1/acta.txt: Unicode text, UTF-8

Lo que debes lograr

Tres valores en tu cabeza:

  • El SHA-256 calculado (64 hex caracteres).
  • La respuesta de -c: OK o FAILED.
  • El tipo de archivo según file.

Después: entrega

  1. Crea el archivo de entrega en el contenedor: 
    mkdir -p ~/trabajo
cat > ~/trabajo/caso1.txt <<EOT
1. SHA-256 calculado: $(pega aqui tu hash)
2. sha256sum -c: OK / FAILED
3. Tipo de archivo (file): pega aqui el tipo
4. Fecha del calculo: $(date -u +%Y-%m-%dT%H:%M:%SZ)
5. La integridad del acta esta demostrada.
EOT
  2. Hacé clic en el botón "Entregar Caso 1 →" debajo. Se abre un GitHub Issue con un formulario que te pide tu nombre, correo institucional y los valores que acabás de calcular.
  3. Pegá el contenido de ~/trabajo/caso1.txt.
  4. Al enviar, queda Issue público con tu nombre y fecha.

Caso 2 · Adquisición y cadena de custodia

Práctica guiada: copia forense verificada con hash sobre una imagen FAT32 de 128 MB.

Objetivo

Generar una copia forense verificada con hash de una imagen FAT32 y verificar el directorio de archivos de evidencia.

Herramientas que vas a usar

ComandoQué hacePertenece a
fileIdentifica el tipo de archivo (incluido el filesystem FAT32/NTFS/ext4).GNU file
sha256sumCalcula hash SHA-256 de cualquier archivo.GNU coreutils
hashdeep -rCalcula los hashes de todos los archivos de un directorio recursivamente.md5deep / hashdeep
hashdeep -r -kVerifica los hashes de un directorio contra una lista guardada.md5deep / hashdeep
dc3ddCopia forense que calcula el hash DURANTE la copia, no después.dc3dd (NIST)
flsLista archivos de una imagen de filesystem (Sleuth Kit).The Sleuth Kit

Qué hace un forense real

En un caso real, el perito recibe un disco o USB. Lo conecta con un bloqueador de escritura (hardware que evita que se escriba en él). Calcula su hash. Hace una copia bit a bit con dc3dd, que recalcula el hash durante la copia. Compara los dos hashes: si son iguales, la copia es íntegra. Sobre esta copia se hace todo el análisis (los pasos 2-4 del curso), NUNCA sobre el original. Aquí nuestro "disco" es una imagen .img ya copiada dentro del contenedor, y "el alumno" simula el flujo copiando a ~/trabajo.

Paso 1 · Identificar la imagen

file /evidencia/caso2/caso2-fat32.img

Debe decir algo como DOS/MBR boot sector ... FAT (32 bit) ... label: "CASO02 ". Eso confirma que es una imagen válida.

Paso 2 · Calcular el SHA-256 de la imagen

sha256sum /evidencia/caso2/caso2-fat32.img

Anota el hash. Lo necesitás en el Paso 5 para verificar la copia.

Tarda ~2 minutos porque la imagen son 128 MB.

Paso 3 · Hash recursivo del directorio

Herramienta

hashdeep -r <directorio> > lista.txt — calcula hashes de cada archivo del directorio recursivamente.

hashdeep -r -k lista.txt <directorio> — verifica los hashes contra la lista.

Genera la lista

hashdeep -r /evidencia/caso2/evidencia_original/ > ~/trabajo/caso2-hashes.txt
cat ~/trabajo/caso2-hashes.txt

Vas a ver ~7 líneas con el formato <hash>,<tamaño>,<ruta>.

Verifica

hashdeep -r -k ~/trabajo/caso2-hashes.txt /evidencia/caso2/evidencia_original/

Salida esperada: una línea OK por archivo. Si alguna dice FAILED, hubo alteración.

Paso 4 · Copia forense con dc3dd

Herramienta

dc3dd if=ORIGEN of=DESTINO hash=sha256 hashlog=BITACORA log=BITACORA bs=4M — copia bit a bit calculando hash en el momento.

Escribe esto

dc3dd if=/evidencia/caso2/caso2-fat32.img \
      of=~/trabajo/caso2-copia.dd \
      hash=sha256 \
      hashlog=~/trabajo/caso2-copia.hashes \
      log=~/trabajo/caso2-copia.log \
      bs=4M

Las opciones

  • if= archivo origen (input file).
  • of= archivo destino (output file).
  • hash=sha256 calcula SHA-256 durante la copia.
  • hashlog= archivo donde guarda la huella calculada.
  • log= bitácora de la operación.
  • bs=4M lee y escribe en bloques de 4 MB (más rápido).

Vas a ver

Una barra de progreso y al final la línea con el hash calculado. Lo compara con el del archivo original (Paso 2) automáticamente.

Si dc3dd da error, aseguráte de tener espacio en disco: df -h ~/trabajo.

Paso 5 · Verificar la copia

Compara hashes

grep -i "sha256" ~/trabajo/caso2-copia.hashes
diff <(sha256sum ~/trabajo/caso2-copia.dd | awk '{print $1}') \
     <(grep -oE "[0-9a-f]{64}" ~/trabajo/caso2-copia.hashes)

Si diff no imprime nada, los hashes son idénticos: la copia es íntegra.

Bonus · Lista los archivos de la imagen

Mientras dc3dd copia, abrí otra terminal y corré fls:

fls -r /evidencia/caso2/caso2-fat32.img | head -20

Vas a ver 8 entradas del directorio raíz (volumen + 7 archivos). Ejecutá también fls -r /evidencia/caso2/caso2-fat32.img | grep papelera para encontrar los 3 archivos del directorio papelera/.

Lo que debes lograr

  • El SHA-256 original de la imagen (Paso 2).
  • Confirmación de que todos los archivos del directorio coincidieron con hashdeep.
  • Una copia local bit-a-bit idéntica (Paso 5).
  • El listado de los 3 archivos de la papelera simulada.

Después: entrega

  1. Crea el mini-informe: 
    cat > ~/trabajo/caso2.txt <<EOT
1. SHA-256 original: $(pega el hash)
2. hashdeep OK en N de N archivos
3. Copia integra con dc3dd: OK
4. Archivos regulares en la imagen: $(wc -l de fls -r | grep '^r/r')
5. Conclusión: copia integra
EOT
  2. Crea también ~/trabajo/caso2-papelera.md con la lista de los 3 archivos de la papelera.
  3. Hacé clic en "Entregar Caso 2 →" y completá el formulario de GitHub Issues.

Caso 3 · Análisis de sistemas de archivos y SO

Práctica guiada: examinar la MFT de un volumen NTFS sin montar la imagen.

Objetivo

Listar archivos del directorio raíz de un volumen NTFS, leer metadatos de la MFT por inode, e identificar archivos borrados o con flujos alternos.

Herramientas que vas a usar

ComandoQué hacePertenece a
fileIdentifica el filesystem (NTFS, FAT, ext4...).GNU file
flsLista archivos de un volumen (directorio raíz por default).The Sleuth Kit
fls -dLista solo archivos borrados (metadata persiste en MFT).The Sleuth Kit
istat <inodo>Muestra metadatos de un inodo (tipo, tamaño, timestamps, ADS).The Sleuth Kit
icat <inodo>Extrae el contenido de un inodo (incluso archivos borrados).The Sleuth Kit
fsstatMuestra metadata del filesystem (versión NTFS, OEM, etc.).The Sleuth Kit

Qué hace un forense real

En un caso real, el perito NO monta la imagen NTFS en su equipo de análisis: montarla modifica los timestamps de acceso. En su lugar, usa herramientas que leen la imagen directamente (Sleuth Kit, Autopsy, EnCase). Cada archivo en NTFS tiene un inodo en la MFT (Master File Table) con sus metadatos y sus flujos de datos. NTFS permite múltiples flujos por archivo (Alternate Data Streams), muy usados por malware para esconder código. fls y istat son las herramientas de bajo nivel para esto.

Paso 1 · Identificar el filesystem

file /evidencia/caso3/caso3-ntfs.img

Debe decir "NTFS, ..." con la versión, OEM, etc.

Paso 2 · Listar el directorio raíz

fls /evidencia/caso3/caso3-ntfs.img

Vas a ver

r/r 23: archivo1.txt
r/r 24: archivo2.txt
...
* r/r 30: archivo_borrado.txt   (asterisco = borrado)
v/v 25: subdirectorio

La primera columna indica el tipo: r/r=archivo regular, v/v=directorio, *=borrado.

Cuenta cuántos r/r hay:

fls /evidencia/caso3/caso3-ntfs.img | grep -c "^r/r"

Paso 3 · Inspeccionar metadatos

Elige un inodo de los que viste (por ejemplo el 23).

istat /evidencia/caso3/caso3-ntfs.img 23

Vas a ver

Tres bloques de información:

  1. Tipo, ID, formato, modo de acceso, tamaño.
  2. Links, UID, GID.
  3. Timestamps (creación, modificación, acceso, modificación de MFT), flags.

Si tiene ADS (flujos alternos), aparece una sección "$STANDARD_INFORMATION" y "$FILE_NAME". Solo NTFS soporta múltiples flujos.

Paso 4 · Detectar archivos borrados

fls -d /evidencia/caso3/caso3-ntfs.img

Solo aparecen archivos borrados. Su metadata sigue en la MFT hasta que otro archivo sobrescriba ese bloque.

Para recuperar el contenido:

icat /evidencia/caso3/caso3-ntfs.img 30 > ~/trabajo/recuperado.bin
file ~/trabajo/recuperado.bin

(Sustituye 30 por el inodo real del archivo borrado). Si el espacio no fue sobrescrito, recuperás el contenido original.

Lo que debes lograr

  • Confirmar que el filesystem es NTFS (Paso 1).
  • Contar archivos vivos del directorio raíz (Paso 2).
  • Para un inodo específico: tamaño, fecha de creación, presencia de ADS (Paso 3).
  • Contar archivos borrados (Paso 4).
  • Si uno de ellos es recuperable con icat y por qué.

Después: entrega

  1. Mini-informe en ~/trabajo/caso3.txt con las seis líneas que indica la checklist anterior.
  2. Si encontraste ADS, ~/trabajo/caso3-flujos.md con el detalle de qué flujos alternos había y para qué archivo.
  3. Clic en "Entregar Caso 3 →".

Caso 4 · Forense de redes y memoria

Práctica guiada: detectar malware en un PCAP y capturar la memoria de un proceso en vivo.

Objetivo

Detectar patrones de actividad maliciosa (DGA, C&C, túnel DNS) en una captura de red, y capturar la memoria de un proceso simulado para analizarla con Volatility 3.

Herramientas que vas a usar

ComandoQué hacePertenece a
tsharkLee archivos PCAP. Filtra por IP, puerto, protocolo, campo.Wireshark (CLI)
incidenteLevanta un proceso simulado que genera tráfico de C&C.script del laboratorio
capturar-memoriaVolca la memoria del proceso con gcore + calcula SHA-256.script del laboratorio
volVolatility 3: analiza dumps de memoria (procesos, conexiones, archivos).Volatility (Python)
stringsExtrae cadenas de texto legibles de archivos binarios.GNU binutils
gcoreVolcado de memoria de un proceso en formato ELF Core.GNU debugger (gdb)

Qué hace un forense real

En un caso real, el perito recibe dos tipos de evidencia: capturas de tráfico (PCAP de tcpdump/Wireshark del firewall corporativo) y volcados de memoria (AVML, LiME). En redes, los indicadores típicos de malware son: dominios generados por algoritmo (DGA), conexiones repetidas a IPs fijas (C&C), y túneles DNS para exfiltración. En memoria, los indicadores son procesos no listados en la lista oficial, conexiones a IPs sospechosas, y cadenas de texto con URLs, IPs o comandos cifrados parcialmente. Aquí dejamos que el contenedor genere un proceso "incidente" pedagógico para que lo captures y analices.

PARTE A · Análisis de tráfico (PCAP precargado)

Paso 1 · Inspeccionar la captura

tshark -r /evidencia/caso4/red_caso4.pcap -c 5

Vas a ver

5 paquetes. Los primeros son consultas DNS, conexiones TCP al puerto 8443, etc.

Paso 2 · Contar consultas DNS

tshark -r /evidencia/caso4/red_caso4.pcap -Y "dns" | wc -l
tshark -r /evidencia/caso4/red_caso4.pcap -Y "dns.flags.response == 1" | wc -l

Primer número: total de paquetes DNS. Segundo: cuántos son respuestas.

Paso 3 · Encontrar dominios DGA-style

Dominios generados por algoritmo: 16+ caracteres hexadecimales + .test.

tshark -r /evidencia/caso4/red_caso4.pcap \
       -Y "dns.qry.name matches '[0-9a-f]{16,}\\.test'" \
       -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head -10

Vas a ver

Listado de dominios hexadecimales con su frecuencia. Estos son los DGA.

Paso 4 · Identificar el canal de C&C

Patrón: conexiones repetidas a la misma IP en intervalos regulares (~60 segundos en este caso).

tshark -r /evidencia/caso4/red_caso4.pcap \
       -Y "tcp.dstport == 8443" \
       -T fields -e frame.time_epoch | head -10

Toma tres timestamps y restalos. Si son ~60s, es C&C.

Paso 5 · Identificar el túnel DNS

tshark -r /evidencia/caso4/red_caso4.pcap \
       -Y "dns.qry.name matches 'exfil_chunk.*tunnel.example.test'" \
       -T fields -e dns.qry.name | head -5

Subdominios de 40+ caracteres hexadecimales dentro de tunnel.example.test son el túnel.

PARTE B · Captura de memoria del proceso

Paso 6 · Levantar el proceso incidente

Abrí una terminal en el contenedor (la pestaña "Cómo correr el laboratorio" arriba te dice cómo con docker exec). En esa terminal:

incidente

El proceso queda corriendo. Verás líneas como:

[12345] intento conexion a 203.0.113.50:8443 a las 14:32:15
[12345] intento conexion a 203.0.113.50:8443 a las 14:32:20
...

NO es malware real: es un proceso que genera tráfico simulado para que lo analices.

Paso 7 · Capturar la memoria

Abrí una SEGUNDA terminal al contenedor (otra pestaña o docker exec con otra sesión):

capturar-memoria

Vas a ver

== Capturando memoria del proceso 'incidente' ==
PID encontrado: 12345
Usuario: perito
Comando: python3 ...
Dump generado: /home/perito/trabajo/memoria_incidente_20261018_073000.core
Tamaño: 12 MB
SHA-256: a4b2c3d4e5f6...
...

Guarda el SHA-256: lo necesitás para la entrega.

Paso 8 · Analizar el dump con Volatility 3

En la misma terminal, ahora que ya tenés el dump:

vol -f ~/trabajo/memoria_incidente_*.core linux.pslist
vol -f ~/trabajo/memoria_incidente_*.core linux.pstree
vol -f ~/trabajo/memoria_incidente_*.core linux.netscan

Qué buscar

  • pslist: ¿está el proceso incidente en la lista de procesos?

Caso 5 · Dictamen pericial integrador

Práctica guiada: redactar el dictamen con las nueve partes del CGP artículo 226.

Objetivo

Redactar un mini-dictamen pericial formal de 600 a 1200 palabras, citando la evidencia de los casos 1 a 4, y cerrando con las diez declaraciones bajo juramento.

Herramientas que vas a usar

Ninguna herramienta técnica. Vas a usar:

  • Un editor de texto (nano, vim, o el editor Markdown de tu elección) dentro del contenedor o en tu computador.
  • Un navegador para pegar el contenido en el formulario de Issue.

Qué hace un forense real

En un caso real, el dictamen pericial es un documento técnico-legal que:

  1. Identifica al perito y su matrícula.
  2. Repite la solicitud del fiscal o juez.
  3. Plantea qué debe responder.
  4. Cita el marco legal aplicable (Ley 906 arts. 415/417/420, CGP art. 226, normas técnicas).
  5. Describe la metodología y las verificaciones de integridad.
  6. Lista hallazgos con números (hashes, conteos, fechas) — NUNCA con adjetivos.
  7. Interpreta qué significa cada hallazgo.
  8. Concluye directamente sobre el objeto del dictamen.
  9. Firma bajo juramento, con las diez declaraciones del art. 226 CGP.

La sustentación oral en la audiencia se evalúa sobre estas nueve partes. Por eso el sílabo del curso las tomó como la columna vertebral del documento.

Paso 1 · Crear el archivo de dictamen

nano ~/trabajo/caso5-dictamen.md

(o usa vim, code, o lo que prefieras)

Paso 2 · Redactar las nueve partes

Encabezado (cabecera)

DICTAMEN PERICIAL
==================

Perito: Tu Nombre Completo
Matricula: Tu Matricula
Fecha: 2026-MM-DD
Lugar: Medellín, Colombia
Caso: UdeC-2026-001

1. Identificación del perito

Tu nombre, cédula, matrícula profesional, lugar y fecha.

2. Solicitud

Una frase: "Se solicita al perito dictamen pericial sobre..." (NO más de tres oraciones).

3. Objeto del dictamen

Tres preguntas concretas que el dictamen debe responder. Ejemplo:

  1. ¿El archivo acta.txt mantiene su hash entre el original y la copia?
  2. ¿La copia forense de la imagen FAT32 coincide bit-a-bit con el original?
  3. ¿Qué procesos activos estaban en memoria del contenedor durante la captura?

4. Marco normativo aplicable

Citas literales (con número de artículo):

  • Ley 906 de 2004, art. 415 — Descubrimiento de la prueba pericial.
  • Ley 906 de 2004, art. 417 — Siete temas del interrogatorio al perito.
  • Ley 906 de 2004, art. 420 — Seis criterios de valoración.
  • Código General del Proceso, art. 226 — Nueve partes del dictamen.
  • Ley 1273 de 2009, art. 269A — Acceso abusivo a sistema informático.
  • ISO/IEC 27037, ACPO, RFC 3227.

5. Metodología y verificación de integridad

Herramientas usadas (sha256sum, dc3dd, Sleuth Kit, etc.). Procedimiento del hash. Bitácora resumida.

6. Hallazgos

Cuatro o cinco. Cada uno con:

  • Evidencia citada (nombre del archivo o de la captura).
  • Procedimiento (qué herramienta, qué comando).
  • Resultado numérico (hash, conteo, fecha).

Ejemplo: "Hallazgo 1. El archivo acta.txt tiene SHA-256 9f16b46.... Procedimiento: sha256sum -c. Resultado: OK."

7. Interpretación

Une cada hallazgo con su contexto. Sin adjetivos: evita obviamente, claramente, evidentemente, sin duda, malicioso, sospechoso, "con la intención de", hacker. Sustitúyelos por descripciones o bórralos.

8. Conclusiones

Lista de 3 a 6 puntos. Cada conclusión responde a una pregunta del Objeto (Punto 3) y cita el hallazgo que la sostiene.

9. Firma y cierre

Firma, matrícula, lugar. Y la frase clave:

Declaro bajo juramento que: (1) he examinado personalmente la evidencia; (2) el dictamen refleja fielmente mi análisis; (3) no tengo interés directo en el resultado; (4) no he recibido instrucciones sobre las conclusiones; (5) los métodos utilizados son reconocidos por la comunidad científica; (6) los hechos descritos son exactos; (7) no he omitido nada; (8) las opiniones están fundadas; (9) la cadena de custodia está documentada; (10) cumplo los requisitos del artículo 226 del CGP.

Lo que debes lograr

  • Extensión entre 600 y 1200 palabras.
  • Incluye las nueve partes numeradas.
  • Incluye las diez declaraciones en una sola línea al final.
  • Al menos tres hallazgos con hashes específicos.
  • Menciona evidencia de los casos 1 y 2.
  • Cita al menos tres artículos de ley con número.
  • NO contiene ninguna de las palabras prohibidas.

Después: entrega

  1. Verifica que el archivo no contiene las palabras prohibidas: 
    grep -E "obviamente|claramente|evidentemente|sin duda|malicioso|sospechoso|con la intención de|hacker" \
     ~/trabajo/caso5-dictamen.md
# Si no imprime nada, perfecto.
  2. Cuenta las palabras: 
    wc -w ~/trabajo/caso5-dictamen.md
  3. Clic en "Entregar Caso 5 →" y pegá el contenido completo.
  4. El docente evalúa: presencia de las nueve partes, hashes concretos, lenguaje sobrio, citas legales.
